## I — 方法论骨架 (Interpretation)

群体的有效协作存在一个**硬边界：约 150 人**（邓巴数，源自灵长类社交脑容量推算，人类学家邓巴发现原始部落规模都≈150）。

机制：超过 150，成员间无法维持"熟人信任"，沟通成本骤增、协作退化为官僚低效、责任分散、匿名化导致失序（与 broken-windows 呼应）。

应用：任何需要紧密协作/高信任的单位，把规模控制在 ≤150；超过就**拆分**为子单位，各自有目标与沟通节奏。这不是"越大越强"，而是"恰到好处才高效"。

---

## A1 — 书中的应用 (Past Application)

### 案例 1: 戈尔公司（W.L. Gore）
- **问题**: 创新型企业如何保持小公司的协作效率？
- **方法论的使用**: 规定任何工厂/单位不超过 150 人，超了就分拆成两个各自发展。
- **结论**: 用 150 为组织规模硬上限，维持熟人协作。
- **结果**: 成为"规模边界"管理典范。

### 案例 2: 邓巴的原始部落统计
- **问题**: 人类天然社群规模多大？
- **方法论的使用**: 梳理人类学文献，21 个原始狩猎族群规模都≈150（均值约 147.8）。
- **结论**: 150 是跨文化的社交上限。
- **结果**: 为 150 法则提供人类学证据。

## A2 — 触发场景 (Future Trigger) ★

### 用户会在什么情境下需要 this skill?
1. 新部门/团队规模膨胀，协作变差、沟通失真。
2. 社群/私域/会员产品大到"没人认识没人管"。
3. 组织设计时要决定"何时拆分"。

### 语言信号 (用户的话里出现这些就应激活)
- "团队太大 / 协作差 / 沟通失真"
- "组织膨胀了怎么办"
- "社群大到管不过来"
- "怎么拆分团队/部门"
- "Dunbar's number / group size limit / 150 rule"

### 与相邻 skill 的区分
- 与 `broken-windows`：若失序源于"小窗没人修"，用 broken-windows；若源于"人太多管不过来"，用本 skill。
- 与 `power-of-context`：本 skill 是"环境威力"在规模维度的具体法则；要纠偏性格归因用 power-of-context。
- 与 `connectors`：connectors 解决"跨圈扩散"，本 skill 解决"单位内协作上限"。

## E — 可执行步骤 (Execution)

1. **评估当前单位规模**
   - 完成标准: 数出需紧密协作的成员数，判断是否 >150。
2. **设定 150 硬上限**
   - 完成标准: 把"单位 ≤150"写进组织/社群设计规则。
3. **超员即拆分**
   - 完成标准: 每超 150 拆为子单位，各给独立目标、负责人、沟通节奏。
4. **保熟人信任机制**
   - 完成标准: 子单位内维持可面对面、可点名、责任到人的结构。
   - 判停条件: 若协作差但规模≤150，则问题不在规模，转 broken-windows / power-of-context。

## B — 边界 (Boundary) ★

### 不要在以下情况使用 this skill
- 群体是"松散关注/订阅"关系而非"紧密协作"——订阅型产品可远超 150（如公众号读者）。
- 问题在信息包装——用 stickiness-factor。
- 问题在微小失序——用 broken-windows。

### 作者在书中警告的失败模式
- 盲目扩张规模追求"越大越强"，导致熟人社会退化为官僚低效。

### 作者的盲点 / 时代局限
- 邓巴数来自前数字时代；远程协作/异步工具可能把"有效协作上限"抬高或改变形态，需结合工具实际校准，勿机械套用。

### 容易混淆的邻近方法论
- 与 broken-windows 混淆：一个管"规模"，一个管"小失序信号"，常同时需要。
