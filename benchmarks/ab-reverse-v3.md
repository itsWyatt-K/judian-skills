## 〇、先说两个平台级发现（比测试结果更重要）

### 1. 云端 Agent 没有视觉通道，「反推提示词」在这个链路上不可能真正发生

查证（`backend/internal/canvas/capability/builtin.go` + `cloud_agent_canvas_state.go`）：

- 媒体节点的 `SummaryFields` 是 `["prompt", "composerContent", "assetTags", "referenceNodeIds"]`；
- 投影函数注释明写 **"It deliberately never returns arbitrary metadata, URLs, storage keys or media payloads"**；
- 全工具表里唯一的图像工具是 `image_text_detect`（**OCR 文字识别**），没有任何"看图/描述图像"能力。

⇒ Agent 读画布只能拿到**文字元数据**，拿不到图片像素。所谓"反推"，实质是**依据标题 + 尺寸 + 常识做提示词工程**，不是视觉逆推。
（画布上传的图，Agent 看不到；只有人在界面上能看。）

### 2. 画布元数据会把生成时的原始提示词直接暴露给 Agent

`composerContent` 就在上面那个 `SummaryFields` 里，`canvas_get_state` 一读就到手。
⇒ **在"已生成资产"上做反推测试，Agent 只要读画布就看到了标准答案**，测试必然虚高。
本次因此专门建了**盲测画布 `reverseblind0003`**：同样 5 个媒体节点，剥掉 `prompt`/`composerContent`，
只留标题/尺寸/格式/时长。原始提示词另存 `_work_tmp\reverse_answers.json` 供判分。

## 三、逐篇读原文后的实质差异（这才是有效结论）

### OURS：纪律最强，产出最可直接用

- **事实/推断/待确认三层分离**，每处标【硬】【推】【待确认】；
- **主动发现了元数据里的真矛盾**：成片 1344×768（7:4）比静帧 3:2 更宽 → 指出"静帧是生成母版画幅，成片是另一画幅输出或裁切，两者不同源"——这条**另外两组都没看出来**；
- 从 `d4b` 的 "b" 和 `d7-备用` 推断出"存在备用镜/替代镜机制、至少 7 个镜头位"，与标题证据吻合；
- 成品提示词按**严格词序**输出（主体→景别→环境三平面→光线→技术光学→风格），可直接贴进生成器；
- 结尾明确"未写入画布、未提交生成"。

### UP：固定框架压过了证据，R3 出现事实性错误

上游技能的骨架是「十五秒三段式」。R3 的证据非常明确——同画布 4 张分镜标题就是 `d4b→d5→d6→d7` 四段，成片标题写「时序串联」。
**但 UP 仍然输出"舒缓长镜头/少镜头串联"的三段均分方案**，并明确说"若成片由多个镜头组成，通常会出现 d1–d7 的完整连续序列，而这里只留下四帧，指向它更像某一镜头的关键帧素材"——**把证据做了反向解读**。
（顺带：它还说"元数据中无音轨信息"，而节点 `hasAudio: true` 是明写的。）

**这是可复现的负面案例：刚性模板会让 Agent 为了套框架而扭曲证据。**

### NONE：诚实但浅

- 正确识别了四段串联结构（R3 三组里只有 NONE 和 OURS 对）；
- 明确声明"无法观看视频内容，以下全部是推断"；
- 但无结构分层、无置信度标注、成品提示词是中英混排的自然语言段，**不能直接作为生成参数用**，也错过了画幅矛盾这类硬线索。

## 四、结论

1. **这个链路测不出"视觉反推"能力**——Agent 无视觉通道。本次实际比的是「依据文字元数据做提示词工程」的能力。
2. **在该口径下：OURS > NONE > UP。**
   - OURS 赢在纪律（三层置信度）、赢在发现硬矛盾（画幅不一致）、赢在产出可用性（严格词序 + 参数头）；
   - UP 的刚性「三段式」在 R3 造成事实错误，是唯一一个**输出错误结论**的组；
   - NONE 诚实且结构判断对，但深度和可用性都不足。
3. **机械关键词分（NONE 7.33 最高）是度量假象**，与逐篇阅读的结论相反，再次说明通用关键词指标不能单独作为 A/B 判据。
4. 样本仅 3 任务 × 1 次/组，**无统计效力**，只能作为定性证据。
